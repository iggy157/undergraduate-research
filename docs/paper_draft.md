## タイトル案

第一候補: **How Does Generation Granularity Shape Multi-Party Dialogue? A Controlled Comparison of LLM-Based Simulation Methods**

第二候補: **Batch or Line by Line? Disentangling Prompt Goal, Context Placement and Information Access in LLM-Generated Multi-Party Discussions**

日本語仮題: 生成の粒度は多人数議論の性質をどう変えるか: 単一 LLM による台本生成とマルチエージェント生成の統制比較

## 概要

LLM に複数人の議論を生成させる方法には、1 つの LLM が台本全体を一括で書く方法と、参加者ごとに独立した LLM を置いてサーバ経由で 1 発話ずつ対話させる方法がある。両者の比較は先行研究でも行われているが、方式ごとにプロンプトや進行手続きが異なり、差の原因 (プロンプトの目標、履歴の置き場所、結末の決め手、文脈の分割、情報量) を分離できていない。本研究は、同一モデル・同一ルール文・同一台本文法・同一の情報公開スケジュールのもとで、差分を設計した軸だけに絞った比較基盤を構築し、3 ドメイン (人狼、候補者選定、共同生活の取り決め) × 各 30 設定で 5 条件を比べる: single-batch (台本全文を一括生成)、single-batch-stepped (同じプロンプトを 1 行ずつ刻み、結末はサーバが決める)、single-online (全情報を持つ 1 つの書き手が「次の 1 行」を書く)、multi-public (席ごとの LLM に全員の秘密を開示)、multi-private (席ごとの LLM に自席の秘密のみ)。隣り合う条件の差はそれぞれ「結末と構造の決め手」「プロンプトの目標と履歴の置き場所」「1 つの文脈か席ごとの文脈か」「情報量」に対応する。さらに、同一モデルが設定から書いた結末を含まない筋書き (process plan) を全条件に同文で与え、明示的な計画が各方式の性質をどう変えるかを調べる。議論の質は 6 軸 (全体整合性、局所応答性、相互作用の自然さ、人物一貫性、情報の忠実さ、多様性) で人手評価を主に測り、方式ごとの長所と短所を明らかにする。補助分析として、発話生成直前の隠れ状態から将来属性が復号できる度合いを方式間で比べる。

## 1. はじめに

LLM を用いた多人数議論の生成は、社会シミュレーション、対話データの合成、ゲーム AI に使われる。生成の仕方には、1 回の生成で議論全体を書き下ろす中央集権的な方法と、各参加者を独立した LLM にして逐次に応答させる分散的な方法がある。前者は整合的な台本を書きやすく、後者は参加者が互いに反応する対話になりやすい、と言われるが、既存の比較は方式ごとにプロンプトや進行手続きが異なり、どの差がどの性質を生むのかを特定できない。面接対話では対話エージェント方式が一括生成より高く評価されたという報告 (De Baer et al., GEM 2025) もあり、「どちらが良いか」は設定と観点に依存する。

本研究の問いは「一括生成と逐次生成は、議論のどの性質に対して、それぞれどのような長所と短所を持ち、その差は何によって生じるか」である。自己回帰モデルでは、同じトークン列を一度に生成しても、1 行ずつ止めて同じ接頭辞から再開しても、greedy なら同じ続きが出る。したがって「一括か逐次か」の差は、生成を分割すること自体ではなく、(1) プロンプトの目標 (台本全文を完成させるか、次の 1 行を書くか)、(2) 履歴の置き場所 (自分の出力の続きか、user に貼り直された台本か)、(3) 結末と構造の決め手 (書き手自身か、サーバか)、(4) 文脈の分割 (1 つの全知の文脈か、席ごとの文脈か)、(5) 情報量 (全員の秘密か、自席の秘密か) のどこかから生じる。本研究はこの 5 つを 1 つずつ変えた条件を並べて測る。

**研究課題**

- RQ1 (生成の構成): 一括生成、刻んだ一括生成、逐次の 1 つの書き手、逐次の席ごとの参加者の間に、議論の質の 6 軸でどのようなトレードオフがあるか。差はどの要因 (結末の決め手 / プロンプトの目標と履歴の置き場所 / 文脈の分割 / 情報量) に帰属するか。
- RQ2 (情報と計画): 秘密情報の開示と、結末を含まない明示的な筋書きは、そのトレードオフをどう変えるか。結末を含む筋書きとの違いは何か。
- RQ3 (頑健性と実用): その傾向はドメイン・モデル・decoding を変えても再現するか。計算コストに対してどの方式が有利か。

補助: single-batch の発話前表現からは、他の条件より将来の議論属性が高い精度で復号できるか (復号可能性であって計画の因果ではない)。

**貢献**: (1) 差分を設計した軸だけに絞った比較基盤 (共通ルール文・共通台本文法・席ビューと書き手ビューの決定的復元・違反と正規化の共通記録・vLLM が見たトークン id の記録)。(2) 5 条件で 5 要因を 1 つずつ分離する実験設計と、分割自体が効かないことの実証。(3) 6 軸の人手評価による方式ごとの長所と短所の提示。(4) 結末を含まない筋書きと結末を含む筋書きの効果の分離。(5) 全知の書き手が未公開情報を発話に漏らす現象 (先出し) の定量化。

## 2. 関連研究

**LLM マルチエージェント議論・ゲーム**: 複数 LLM の討論による推論の改善 (Du et al., 2023)、役割分担による協調 (Li et al., 2023, CAMEL)、生成エージェントによる社会シミュレーション (Park et al., 2023)。人狼については LLM エージェントの経験学習 (Xu et al., 2023) と人狼知能大会 (AIWolf / aiwolf-nlp)。

**single と multi の比較**: 面接対話で一括生成と 2 エージェント対話を比べ、LLM 判定では対話方式が高く、トークン数は約 6 倍だった研究 (De Baer et al., GEM 2025)。最後通牒ゲームでの single と multi の人間行動再現の比較 (Sreedhar & Chilton, HICSS 2025)。multi-agent debate の優位が single-agent ベースラインに対して不安定であることを示した研究 (Zhang et al., 2025)、議論の構造的・認知的要因を操作した統制研究 (Wu et al., 2025)。本研究は多人数の自然言語対話の生成を対象に、5 つの要因を 1 つずつ分離する点で異なる。

**多人数対話の生成と評価**: 話題と修辞の整合性による多人数対話生成の改善 (EMNLP 2024)。多人数対話の評価で人間と LLM 判定の一致が低く (κ ≈ 0.11)、LLM 判定が冗長な表現を好み発話順の乱れに鈍いことを示した研究 (Samanta et al., ACL 2026)。本研究の評価設計はこれを前提に人手評価を主にする。

**単一 LLM による複数人格の模擬**: Solo Performance Prompting (Wang et al., NAACL 2024)。本研究の single-batch は台本の一括生成で、人格間の明示的な協調手続きを持たない。

**LLM の内部表現と計画性**: Dong et al. (2025, ICML) は応答生成前のプロンプト表現から応答の属性を線形プローブで予測できることを示した。本研究はこれを補助分析として転用し、復号可能性と計画性を区別する。

**LLM 判定のバイアス**: 位置バイアス (Zheng et al., 2023)、自己選好 (Panickssery et al., 2024)。

## 3. 比較基盤

### 3.1 ドメインと設定

3 ドメイン、いずれも 5 人。議題は設計上「正解のない」もので、タスク精度は測らない (カードの有利不利は候補ごとに合計 0、人狼は自己対戦)。

| ドメイン | 内容 | 非公開情報 | ラウンド構造 | 決定 |
|---|---|---|---|---|
| 人狼 (aiwolf) | 5 人村 (占い師 1、人狼 1、狂人 1、村人 2) | 役職 | Day 0 (投票なし) → Day 1, 2, … | 毎日投票・処刑、夜に占い/襲撃 |
| 候補者選定 (candidate_selection) | 社内の提案 4 件から 1 件を選ぶ | 各自の関心事 + 調査結果 | Round 1 → 調査 → Round 2 → 選択肢公開 → Round 3 → 投票 | 最多票の候補 |
| 共同生活 (shared_living) | 同居者の取り決め 3 案から 1 案を選ぶ | 同上 | 同上 | 同上 |

各ラウンド 4 ターン、固定の発話順、1 発話 1〜40 語、`Skip` / `Over`。議論ドメインでは Round 1 終了時に各自が 10 件の「調べられる事柄」から 2 件を選び、結果は本人だけに知らされる。ペルソナは 24 人から 5 人を割り当て、設定ファイルで固定。各ドメイン 30 設定。

### 3.2 条件

| 軸 | 値 |
|---|---|
| method | single (LLM 1 つ) / multi (席ごとの LLM) |
| generation (single) | batch (台本全文を 1 回で) / batch-stepped (同じプロンプトのまま、台本を自分の書きかけとして 1 行ずつ続ける。結末と構造はサーバが決める) / online (進行に合わせて「次の 1 行」を書く。台本は user に貼り直す) |
| information (multi) | private (自席の秘密のみ) / public (全員の秘密を全席に開示) |
| plan | なし / process / outcome / outline / turn |

| 条件 | 役割文 | system の残り | user (+ assistant) | 結末の決め手 |
|---|---|---|---|---|
| single-batch | 「あなたはこの議論の書き手」 | 共通ブロック + 5 人の人物欄 (役職/関心事) + 隠された情報 (選択肢・カード全文) | 台本全文の要求 + 出力形式 | 書き手 |
| single-batch-stepped | 同上 | 同上 | 同上 + assistant = それまでの台本 (書き手ビュー) と次の札 (続き書き) | サーバ |
| single-online | 「あなたはこの議論の書き手で、1 行ずつ書く」 | 同上 | 書き手ビュー + `- **X**:` | サーバ |
| multi-public | 「あなたは参加者 X」 | 同上 | 席 X の台本 (席ビュー) + `- **X**:` | サーバ |
| multi-private | 「あなたは参加者 X」 | 共通ブロック + 自席の人物欄 | 同上 | サーバ |

隣り合う条件の差 (梯子):

| 比較 | 変わるもの |
|---|---|
| single-batch vs single-batch-stepped | 結末と構造の決め手 (書き手 vs サーバ) だけ。接頭辞のトークン列は同一で、greedy ならサーバが差し替えない限り同じ発話が出る。数値的な非決定性 (vLLM のバッチ構成による近接確率の反転) の大きさもここで測る |
| single-batch-stepped vs single-online | プロンプトの目標 (全文か次の 1 行か) + 履歴の置き場所 (assistant の続きか user の貼り直しか) |
| single-online vs multi-public | 1 つの全知の文脈か、席ごとに分割された文脈か |
| multi-public vs multi-private | 情報量 (全員の秘密か自席の秘密か) |

single-batch と multi-public と single-online の system は役割段落だけが違い、single-batch-stepped は single-batch と同一の system と user を使う (検証スクリプトが 90 設定で確認)。multi-public は「自然なマルチエージェント」ではなく情報アクセスを操作した診断用条件であり、人狼では「知っていて知らないふりをする」ことでゲームの前提が変わることを明示する。

### 3.3 統制

| 項目 | 統制の内容 |
|---|---|
| モデル | 同一モデル、同一 decoding (本体は greedy)、思考モード無効、revision / 精度 / ライブラリ版を固定記録 |
| ルール文 | 4 ブロックを 1 本のテンプレートから全条件に展開し、バイト一致を自動検証 |
| 台本文法 | 全条件が同じ Markdown 文法。席ビューと書き手ビューはログから決定的に復元でき、エージェントが実際に受け取った user / assistant とバイト一致することをテストで保証 |
| 情報公開 | スケジュール表に「いつ・誰に・何が知らされるか」を明記。single には先出し禁止、multi には席ビューで同じタイミングに同じ内容 |
| 発話の境界 | 1 行ずつの条件は同じ停止列 (次の台本要素) で切る。発話内の改行は禁止しない |
| 違反と正規化 | 全条件のログを同じ CSV に変換し、同じ検出器で違反と正規化を記録 |
| 投票 | サーバ集計 (multi / online / stepped) と書き手集計 (batch) を同じ同票規則で扱い、不一致を記録 |
| 記録 | 全 LLM 往復、vLLM が見たプロンプトのトークン id、生成トークン id と対数確率、sampling 設定、条件札 |

### 3.4 筋書き

設定ごとに同一モデルが greedy で 1 本書く (台本からは作らない)。中身を「過程」と「結末」に分け、4 種類を派生する。

| 種類 | 中身 | 与えられる条件 |
|---|---|---|
| process (主系) | 各期間の公開の筋 (話題・論点・意見の傾き) + 席ごとの立場の推移。**票・処刑・採択・夜の行動・勝敗を含まない** | 全条件 (multi-private を含む) |
| outcome | 票・処刑 (採択)・夜の行動・勝敗だけ | public 条件 |
| outline | process + outcome | public 条件 |
| turn | outline + 各ターン各席の発言要旨 (上限条件: 発話内容をほぼ与える) | public 条件 |

生成は turn を 1 本だけ作り、他は削って派生する (入れ子の統制)。検証はルールで機械的に再生 (票 → 同票規則 → 処刑 → 勝敗、対象の生存、発言単位の整合) し、公開の筋と席の筋に結末語がないことも確認する。両方式とも system の末尾に `## Plan` として同文で置き、進行は強制せず、乖離を両方式共通の検出で記録する。計画の効果 (process) と未来情報の効果 (outcome) を分けて測る。

## 4. 実験 1: 生成の構成 × 情報 × 計画

### 4.1 条件と規模

中核 5 条件 × 3 ドメイン × 30 設定 = 450 局。筋書き: process を主系に single-batch / single-online / multi-public / multi-private の 4 条件 (360 局)、outcome を single-batch と multi-public (180 局)。outline / turn は結果を見て single-batch と multi-public で追加。decoding は greedy で統一し、各ドメイン 10 設定をモデルの既定 sampling で再実行して方式 × decoding の交互作用を確認する。

### 4.2 評価

6 軸に分け、人手で測れる軸は人手を主、LLM 判定を補助にする (Samanta et al. の κ ≈ 0.11 を踏まえる)。

| 軸 | 対象 | 主な測り方 |
|---|---|---|
| Global coherence | 議論全体の整合性、結論に至る過程 | 人手 (対比較) + 矛盾率 |
| Local responsiveness | 直前の質問や反論への応答 | 人手 + 名前での呼びかけ・前発話の語の引き継ぎ |
| Interaction realism | 意見の対立、交渉、応答の自然さ | 人手 |
| Persona consistency | 各参加者の立場・性格の一貫性 | 人手 + 立場変更の数と契機 |
| Information fidelity | 秘密情報の扱い、根拠が設定と矛盾しないか、票が立場と整合するか、先出し | 機械 (調査結果の共有率、設定との照合、先出し率) + 人手検証 |
| Diversity | 発言内容・立場・展開の多様性 | 機械 (長さ補正した語彙多様性、重複) |

手続き指標 (違反率・正規化率、発話長、Skip/Over 率、内容ゼロのラウンド、計算コスト) は別に報告する。発話の長さは共変量として扱い、長さを揃えた分析を補助として併記する。LLM 判定は別系統のモデルで順序を入れ替えて 2 回行い、人手との一致率を報告する。

**統計**: 検定単位は設定。対応のある比較に paired bootstrap、二値指標に McNemar、ドメイン・設定の階層性を考慮する混合効果モデル。効果量と 95% 信頼区間を主、p 値を従。「ほぼ同じ」の主張には事前に同等性マージンを定める。一次指標 (6 軸の人手評価) と主要比較 (梯子の 4 対 + single-batch vs multi-private) を実行前に固定し、他は探索的分析とする。ドメイン別の結果も報告する。

主張の形 (向きは実測で決まる): (a) 全体整合性は single-batch が高く、局所応答性と相互作用は multi が高い、というトレードオフ。(b) single-batch と stepped の差は数値的な非決定性と同程度で、分割自体は効かない。(c) 梯子のどの段で各軸が動くかを示し、整合性の差はプロンプトの目標と履歴の置き場所、応答性の差は文脈の分割に主に帰属する (仮)。(d) 情報量 (public vs private) は情報忠実さ以外をほぼ動かさない (同等性マージン内)。(e) process plan は整合性の差を縮め、応答性を落とさない。outcome plan は整合性をさらに上げるが情報忠実さを下げる (結末に合わせた発話)。(f) 先出しは一括生成に固有で、筋書き経由でも弱く現れる。(g) 既定 sampling でも順序は変わらない。

## 5. 補助分析: 発話前表現の将来属性の復号可能性

Dong et al. (2025) に従い、発話生成直前の隠れ状態から将来属性を線形プローブで復号する。取得は記録済みのプロンプトのトークン id と生成トークン id を同じモデルに流し込む再生で行い (vLLM が見た列と同一)、位置は (i) 札トークン (`- **X**:` の末尾。batch と stepped では次の行の最初のトークンを予測する位置) と (ii) 生成直前のプロンプト末尾 (online / multi では生成プロンプトの末尾) の両方を取る。

- 恒等性の検査: single-batch と single-batch-stepped は同じトークン列なので表現が一致する (数値誤差の範囲)。これが「分割自体は効かない」ことの表現レベルの実証。
- 対象: 5 条件 (+ process)。greedy、各ドメイン 100 局。ラベルは語数、Skip/Over、最終投票先、処刑/採択、呼びかけ先。「入力から既に決まる属性」と「後続生成に依存する属性」に分けて報告。
- 統制: 入力情報だけの予測器をベースラインに置き、層の選択は開発データで行い、同一履歴の再生 (single-batch の台本を他条件の形式に流し込む) で文脈を揃える。
- 主張は「復号可能性」にとどめる。差があっても、それがプロンプトの目標と履歴の置き場所に伴う表現の違いなのか、計画と呼べるものなのかは区別しない。

**表 5-1 (仮)**: single-batch で最終投票先 0.77、single-batch-stepped 0.76、single-online 0.45、multi-public 0.44、multi-private 0.41、入力のみ 0.39。

## 6. 今後の展開 (本稿の範囲外)

single-batch の発話前表現を小型の multi エージェントに蒸留し、大会プロトコル (aiwolf-nlp-server) で動作するエージェントを作る研究は、同じ基盤の上で別の研究単位として進める。本稿の設計はそれを見据えて、表現の位置対応 (行単位)、情報を揃えた教師 (multi-private の表現)、秘密の漏洩率 (先出し検出) を確保している。

## 7. モデル計画

| 役割 | モデル | 理由 |
|---|---|---|
| 主系 (全条件、筋書き、プローブ) | gemma-4-31B-it (dense, 60 層) | パイロット済み |
| 別系統 (中核 5 条件) | Qwen3.8-27B (dense, hybrid attention, Apache 2.0) | 同規模の最新の別系統。手元にあり、vLLM 対応を確認済み |
| 別サイズ (中核 5 条件) | gemma-4-12B-it (unified architecture, 48 層) | 同系列の別サイズとしての頑健性 (パラメータ数だけの統制ではない) |

- decoding: 本体は greedy。頑健性は各モデルの generation_config の既定 (Gemma 4: 1.0 / 0.95 / 64)。思考モードは全モデルで無効 (Gemma 4 は chat template の既定で無効、空の思考チャネルが生成プロンプトに付く。Qwen3.8 は `enable_thinking: false` と `preserve_thinking: false` を明示)。chat template、停止列、最大トークン、checkpoint revision、精度 (bf16)、推論ライブラリの版を header に記録する。
- 「モデル横断」の主張は中核条件の現象の再現に限定し、筋書きとプローブの結論は主系に限る。モデル × 方式の交互作用 (gemma で大きく Qwen で小さい等) はそれ自体を結果として報告する。

## 8. 議論と限界

- **分割と表現**: 自己回帰モデルでは生成の分割自体は出力を変えない。差はプロンプトの目標・履歴の置き場所・結末の決め手・文脈の分割・情報量に帰属させる設計にしたが、single-batch-stepped と single-online の差は「目標」と「置き場所」をまとめて含む (さらに分けるには online の役割文を batch の履歴置き場で使う条件が要る。将来課題)。
- **目的関数の違い**: single-batch は「整合的な架空の議論を書く」課題、multi-private は「与えられた情報で意思決定する」課題であり、文面を揃えても解消しない。本研究は議論の質の 6 軸で両者を記述し、意思決定の質は主張しない。
- **multi-public**: 診断用条件。人狼ではゲームの前提が変わる。
- **筋書き**: 生成モデル自身が設定から書く。結末を含まない process が主系で、outcome の効果は未来情報の効果として分けて報告。乖離は記録し、乖離なし部分集合は補助。
- **非決定性**: vLLM の greedy はバッチ構成で近接確率が反転しうる。single-batch と stepped の比較でその大きさを測り、「再現可能」は「ほぼ」と但し書きする。
- **評価**: 人手評価の規模は限られる (各ドメイン 10 設定 × 主要比較、評価者 3 名、一致率を報告)。LLM 判定は補助。
- **一般性**: 5 人、英語、24 ペルソナと固定議題。未知の議題での汎化評価は少数にとどまる。

## 9. 結論

生成の粒度の差を 5 つの要因に分解する統制基盤を構築し、一括生成と逐次生成が議論のどの性質に長所と短所を持つかを 6 軸で示した。分割自体は効かず、差はプロンプトの目標と履歴の置き場所、文脈の分割に帰属した。結末を含まない筋書きは整合性の差を縮めつつ応答性を保ち、結末を含む筋書きは整合性を上げるが情報の忠実さを下げた。全知の書き手は未公開情報を発話に漏らしやすい。
